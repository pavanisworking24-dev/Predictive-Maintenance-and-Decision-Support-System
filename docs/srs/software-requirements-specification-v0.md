**Project:** Conversational Predictive Maintenance and Decision Support System  
**Document:** SRS v0.1 (milestone M0 deliverable)  
**Status:** Draft for team review  
**Date:** 24 October 2026

This specification is based on the project scope (version 2, including the revised coverage criterion, out-of-fold calibration and the Experiment B protocol), `docs/api/openapi.yaml`, `docs/contracts/health-summary-v0.schema.json`, `docs/database/database-schema-v0.sql`, `docs/architecture/risk-and-alert-rules-v0.md` and `docs/architecture/rag-decisions-v0.md`. When this document and the scope disagree, resolve it in the scope first and then update this file.

## 1. Introduction

### 1.1 Purpose

This document defines what the system shall do and the qualities it shall have, so that the five team members, the reviewers and the tests share one definition of "done". It is written for the team, the project guide and the reviewers.

### 1.2 Scope

The product is an explainable predictive-maintenance platform. It learns degradation patterns from the NASA C-MAPSS turbofan data, estimates Remaining Useful Life (RUL) and failure risk with calibrated uncertainty, explains predictions with SHAP, retrieves technical knowledge with retrieval-augmented generation (RAG), and answers questions through a grounded conversational assistant. It is delivered as one tested, containerized, cloud-deployed full-stack application (React frontend, FastAPI backend, PostgreSQL with pgvector).

The system is a research-oriented decision-support platform evaluated on **simulated** data. It does not provide certified maintenance advice. Section 8 lists what the project does not claim.

### 1.5 Conventions

- Requirement statements use "shall". Each has an identifier such as `FR-UQ-02`.
- **Tier** is the scope tier: **Core** (mandatory), **Advanced** (conditional on a stable Core) or **Stretch** (must not delay Core). Anything not listed here is out of scope.
- **Milestone** is the milestone (M0 to M15) in which the requirement is verified.
- **Verification:** T = test (automated or manual), D = demonstration, I = inspection of a document or artifact, A = analysis of measured results.

## 2. Overall description

### 2.1 Product perspective and data flow

The current data flow is **C-MAPSS → batch data processing → prediction → database → dashboard**. The system is not a live telemetry pipeline.

```text
C-MAPSS → data pipeline → feature engineering → XGBoost / baselines
        → RUL + uncertainty + risk → SHAP → Machine Health Summary
        → PostgreSQL → FastAPI → React

Assistant: question → FastAPI → Health Summary + RAG retrieval → LLM → grounded answer
```

The test engines represent the in-service fleet; the training engines are historical run-to-failure references. Inference runs inside the FastAPI backend. A future enhancement (telemetry simulator → MQTT → ingestion → PostgreSQL → prediction → dashboard) is out of scope and is kept distinct from the current flow in all documents.

### 2.2 User classes (simulated)

| Role | Main needs |
|---|---|
| Admin | Manage users, risk thresholds, model versions and the knowledge base; see logs and operational metrics; use every other function |
| Maintenance Manager | Fleet dashboard and report; acknowledge and assign alerts; machine details and the assistant |
| Maintenance Engineer | Machine details, explanations and recommendations; create and update maintenance records; the assistant; the fleet view (view only) |
| Viewer (Advanced) | Read-only access without the assistant |

Appendix A holds the permission matrix.

### 2.3 Operating environment

Developer machines run Docker Compose (Windows, macOS, Linux). The deployment is one AWS virtual machine without a GPU running Docker Compose with the frontend, the backend (with the packaged model artifact) and PostgreSQL with pgvector. Kubernetes and managed-service dependencies are excluded.

### 2.4 Constraints

- All sensor data is simulated; users, maintenance records, alerts and chat records are generated by the application.
- The LLM is a hosted model behind a provider-independent interface (the VM has no GPU), with a spending cap.
- The schedule includes a low-capacity examination month (November), with the go/no-go checkpoints of the scope.
- If the schedule requires cuts, items are removed in this order: Stretch items, Advanced items (starting with Prometheus/Grafana-style monitoring and drift automation), FD004 and FD002 interface refinement (experimental results are kept), role-management refinement. The FD001 end-to-end path is never removed. If M8 is late, the Manager role may be removed.

### 2.5 Assumptions and dependencies

- The C-MAPSS files remain available from the NASA repository.
- A hosted LLM API and an AWS account are available to the team.
- A local sentence-embedding model can run on CPU.
- The team of five works in the ownership areas of the scope, with named backups.

### 2.6 Scope tiers

| Tier | Contents |
|---|---|
| Core | Everything marked Core in Section 3 |
| Advanced | Drift experiment, performance monitoring, model comparison dashboard, automated model registration, health timeline, historical SHAP at sampled cycles, audit logging, Viewer role, production-style API documentation |
| Stretch | LSTM / 1D-CNN benchmark, cross-dataset transfer, automated retraining, advanced drift detection, Prometheus and Grafana, Kubernetes, replay mode |
| Future | Telemetry simulator → MQTT → ingestion pipeline |

### 3.3 Uncertainty quantification

Source: Scope 3.8 and milestone M3.

| ID | Requirement | Tier | Milestone | Verification |
|---|---|---|---|---|
| FR-UQ-01 | The system shall produce a prediction interval `y_hat +/- q`, where q is the ceil((n+1)(1-alpha))/n quantile of absolute calibration residuals. The nominal coverage shall default to 90% and be configurable. | Core | M3 | T |
| FR-UQ-02 | Calibration residuals shall be out-of-fold: training engines are split into engine-level folds (K = 5 by default), each fold is predicted by a model trained on the other folds, and the final model is trained on all training engines. Test engines shall never be used for training, tuning or calibration. | Core | M3 | T |
| FR-UQ-03 | q shall be computed per bin of predicted RUL (Mondrian-style) and shall include late-life calibration samples. | Core | M3 | T |
| FR-UQ-04 | The system shall report empirical coverage and interval width on the official test engines overall, by RUL bin and by subset, with an exact 95% confidence interval for each observed coverage. | Core | M3 | T |
| FR-UQ-05 | A prediction at the training cap shall carry `at_cap = true`, shall be displayed as "≥ 125", and shall not be treated as an actual remaining life by the risk rules. | Core | M4 | T |

### 3.4 Risk assessment and Machine Health Summary

Source: Scope 3.9, section 4.2 and `docs/architecture/risk-and-alert-rules-v0.md`; milestone M4.

| ID | Requirement | Tier | Milestone | Verification |
|---|---|---|---|---|
| FR-RISK-01 | The system shall estimate P(RUL <= N) from the calibration residuals in the same predicted-RUL bin, and shall label it "estimated probability of RUL <= N cycles". It shall never present it as a guaranteed failure probability. | Core | M4 | T |
| FR-RISK-02 | The probability shall be validated with a reliability curve and the Brier score before it is displayed. | Core | M4 | A |
| FR-RISK-03 | The system shall classify each machine as LOW, MEDIUM or HIGH with the active threshold configuration: HIGH if predicted RUL <= high_rul_max or P >= high_probability_min; otherwise MEDIUM if predicted RUL <= medium_rul_max or P >= medium_probability_min; otherwise LOW. | Core | M4 | T |
| FR-RISK-04 | Risk thresholds shall be stored as versioned, immutable configurations (default `cfg-1`), exactly one of which is active. Every risk score shall record the version that produced it. | Core | M7 | T |
| FR-RISK-05 | For evaluation, reference risk labels shall come from the true RUL (HIGH at 30 cycles or less, MEDIUM from 31 to 60, LOW above 60). The system shall report the confusion matrix, HIGH recall, false-alarm rate and lead time. Thresholds shall be tuned on validation data only. | Core | M15 | A |
| FR-RISK-06 | The system shall generate a schema-valid Machine Health Summary for every FD001 test engine, and for the other subsets through the batch workflow. | Core | M4 | T |
| FR-RISK-07 | A Health Summary shall contain `machine_id`, `dataset_id`, `cycle`, `model_version`, `rul` (with `estimate` and `at_cap`), `generated_at` and `disclaimer`. Interval, probability, `risk_level`, `thresholds_version`, trend, contributors and recommendation shall be omitted when unavailable and never invented. | Core | M0 | T |
| FR-RISK-08 | Health Summaries shall satisfy the cross-field rules: interval lower bound <= estimate <= upper bound; `risk_level` and `thresholds_version` present together; and a probability consistent with the interval (if the threshold N is at or above the upper bound the probability is at least the coverage level; if N is below the lower bound it is at most one minus the coverage level). | Core | M4 | T |

## 6. Data requirements

### 6.1 Source data

| Subset | Train / test engines | Operating conditions | Fault modes | Role |
|---|---|---|---|---|
| FD001 | 100 / 100 | 1 | 1 | Development and primary demonstration |
| FD003 | 100 / 100 | 1 | 2 | Fault-mode robustness |
| FD002 | 260 / 259 | 6 | 1 | Operating-condition robustness |
| FD004 | 249 / 248 | 6 | 2 | Combined and most challenging case |

### 6.2 Stored entities

The database has 14 tables: `users`, `machines`, `sensor_readings`, `model_versions`, `predictions`, `risk_threshold_configs`, `risk_scores`, `explanations`, `alerts`, `maintenance_records`, `chat_sessions`, `chat_messages`, `knowledge_documents` and `knowledge_chunks`. C-MAPSS supplies only engines, cycles, operating settings, sensors and RUL information; every other record is generated by the application.

### 6.3 Integrity rules

- A machine is unique by `(dataset_id, engine_id)` and by its readable `machine_code`.
- A reading is unique per machine and cycle; a prediction is unique per machine, model version and cycle.
- At most one model version per dataset is active; exactly one risk threshold configuration is active.
- A risk score references the threshold configuration that produced it.
- Enumerations (roles, risk levels, alert and maintenance status, dataset ids, ingestion status) are enforced by CHECK constraints and match OpenAPI.
- The development seed contains demonstration data only and is never loaded in a deployment.

## 7. Acceptance and evaluation criteria

| Id | Criterion | Requirements |
|---|---|---|
| SC-1 | All three models are evaluated on all four subsets with one reproducible command and one consolidated results table | FR-ML-01, FR-ML-05 |
| SC-2 | For each subset the observed conformal coverage on the official test engines at the 90% nominal level is reported with an exact 95% confidence interval, and the criterion is met when 90% lies inside it. Per-RUL-bin coverage is reported, and deviations beyond ±10 percentage points are discussed as limitations | FR-UQ-04 |
| SC-3 | A probability reliability curve is produced and discussed | FR-RISK-02 |
| SC-4 | RAG gold-set results are reported for retrieval, grounding, correctness and hallucination, with targets set after the first measurement | FR-AST-09 |
| SC-5 | The full demonstration flow completes end to end from a clean Docker Compose start | FR-OPS-04 |

A fixed 85–95% coverage band is not used as pass/fail: with 100 test engines a method with exactly 90% true coverage falls outside it in about 6% of runs, and the chance that at least one of four subsets falls outside is about 14%.

## 8. Out of scope, claims not made and limitations

### 8.1 Claims not made

- Real aircraft telemetry, real-time industrial monitoring, certified aircraft maintenance advice, an actual production fleet deployment, actual production drift.
- A guaranteed failure probability.
- Universal superiority of XGBoost over deep learning, or that FD004 results generalize to every machine.

### 8.2 Out of scope

- Notification channels (e-mail, SMS, push) for alerts.
- Live telemetry ingestion (future enhancement).
- Kubernetes and managed-service dependencies.

### 8.3 Limitations

- All sensor data is simulated.
- Maintenance recommendations are rule-based decision support and do not reflect engineering practice.
- The probability is an approximate, model-derived estimate.
- RUL is capped for training; predictions near the cap carry limited information.
- The knowledge base covers the simulator and the prognostics literature, not real maintenance manuals.
- The cross-conformal calibration has a weaker worst-case guarantee than split conformal prediction; coverage is validated empirically.

## Appendix D. Glossary

| Term | Meaning |
|---|---|
| C-MAPSS | NASA Commercial Modular Aero-Propulsion System Simulation; the simulated turbofan run-to-failure dataset |
| RUL | Remaining Useful Life, in operating cycles |
| RUL cap | Training labels are limited to 125 cycles; predictions at the cap are shown as "≥ 125" |
| PHM08 score | Asymmetric error score in which late predictions are penalized more than early ones |
| Conformal prediction | A method that turns point predictions into intervals using calibration residuals |
| Cross-conformal / CV+ | Conformal calibration with out-of-fold residuals so that every training engine is used |
| Mondrian calibration | Calibration computed separately per bin (here, per bin of predicted RUL) |
| SHAP | Method that attributes a model prediction to its input features |
| RAG | Retrieval-augmented generation: the LLM answers from retrieved documents |
| pgvector | PostgreSQL extension for storing and searching embedding vectors |
| Machine Health Summary | The versioned object that combines RUL, interval, risk, explanation and recommendation |
| Threshold configuration | A versioned set of risk and alert thresholds (default `cfg-1`) |
| Regime | One of the operating-condition clusters in FD002 and FD004 |
